# Phase 1 / P1 行走骨架施工清单

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` or `superpowers:executing-plans` to execute this checklist task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 在不接真实 Binance、不保存真实账户数据的前提下，用 fixture 跑通「市场事实 -> 信号快照 -> 策略计划 -> 账本执行回放 -> 复盘草稿」的最小闭环，并用最小市场页和账本页让人肉眼验证闭环成立。

**Architecture:** P1 采用纵向切片，不按 ledger / signal / strategy 横向做满。先收口快照路径、业务表第一刀和运行时契约校验，再实现 fixture 计算闭环，最后通过 BFF / read model 暴露给只读页面。P1 不接真实 API；真实 Binance、完整账本、完整信号注册表、绩效与周复盘加厚分别交给 P1.5 / P2 / P3 / P6。

**Tech Stack:** Next.js App Router + TypeScript + PostgreSQL + Prisma + Zod + Vitest + Playwright + 独立 Node worker。

---

## 0. 定位

本文是 `Phase1 / P1` 的施工 runbook。它承接 P0 工程骨架，不替代总 PRD、三层 PRD 或 ADR。

- `P0`：工程骨架、验证门、Postgres / Prisma / worker / contracts 基线。
- `P1`：fixture 驱动的三层最小行走骨架。
- `P1.5`：短保留公开市场数据影子采集器，等 P1.1 schema 边界稳定后旁路推进。
- `P2+`：真实账本、真实信号、策略加厚、完整页面和复盘闭环。

P1 的目标是证明系统的核心闭环可运行、可追溯、可展示，不是把完整 Phase 1 做完。

## 2. P1 施工节奏

P1 使用「先全局定边界，再一小节一小节落」的节奏：

1. 先用本 runbook 锁定 `P1.0-P1.4` 的交付物、依赖、验收口径。
2. 每进入一个小节前，再做一次短设计确认，只讨论该小节会实际落地的文件、字段、测试和验收。
3. 每个小节独立分支、独立验证、独立提交，不把后续小节的实现提前塞进来。
4. `P1.0` 和 `P1.1` 必须先完成，后续计算逻辑和页面不得绕过尚未冻结的 schema / snapshot / zod 边界。

推荐小节：

| 小节 | 名称 | 目标 | 是否可并行 |
| --- | --- | --- | --- |
| P1.0 | 契约硬化与快照路径 ADR | 收口 `content_json` / `content_ref`、zod 边界、P1 表第一刀范围 | 不并行 |
| P1.1 | 业务表 migration 第一刀 | 建最小闭环业务表和 DB smoke，不写计算逻辑 | 不并行 |
| P1.2 | fixture 计算闭环 | 用纯函数跑通 signal / strategy / ledger / review | 可按层拆，但需一个闭环 owner 串通 |
| P1.3 | BFF / read model | 页面只消费只读服务契约，不直接拼跨层 SQL | 可与 P1.4 轻度并行 |
| P1.4 | 最小市场页 + 账本页 | 展示 fixture 闭环关键结果，证明人能看懂追溯链 | 依赖 P1.3 |

## 3. P1 完成定义

P1 完成时必须满足：

- 一条测试命令能跑通完整 fixture 闭环。
- Signal 输出 `ActiveSignalSet` 与快照内容。
- Ledger 提供最小决策快照容器、fixture 账户事件、成交归属和策略持仓视图。
- Strategy 读取 `ActiveSignalSet + snapshot_id` 和账本视图，生成 `PlannedAction`。
- Review 生成最小 `ReviewDraft`。
- 市场页展示当前启用态信号、最近快照、输入摘要、数据健康。
- 账本页展示策略持仓、最近成交、归属结果、fixture 同步状态、fixture 对账状态。
- 所有输出能追溯到 `snapshot_id`、`strategy_version` 和账本事件 ID。
- 没有真实 Binance key、真实账户数据、真实 Binance 网络请求。
- `npm run verify` 全绿；修改前端页面的小节还必须 `npm run build` 全绿。
- P1 结束时形成 P2/P3/P4/P5/P6 交接记录。

## 4. P1 不做

- 不接真实 Binance signed endpoint。
- 不接真实账户只读 key。
- 不保存真实账户导出数据。
- 不做自动下单。
- 不做完整绩效 TWR / MWR。
- 不做完整信号注册表 UI。
- 不做真实 collector 的长期调度；P1.5 作为旁路任务单独推进。
- 不做完整策略页和复盘页；P1 只允许在市场页 / 账本页中展示计划动作与复盘草稿摘要。
- 不做非 Binance 数据源。

## 14. Scope Guard

遇到以下需求时，记录到交接或后续计划，不在 P1 顺手实现：

- Binance signed endpoint 接入。
- API key 健康检查真实调用。
- 子账户发现真实调用。
- OI / 多空比长期 collector。
- AI 情绪信号。
- 纸面策略。
- 多策略调度。
- 自动交易或交易所写操作。
- 完整回测。
- 完整绩效与归因分析。

P1 的胜利条件是「走通且可看见」，不是「做宽」。
