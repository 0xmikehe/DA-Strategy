## 第 0 章 定位与边界

### 0.1 信号层职责

信号层回答一个问题：**「市场现在是什么状态」——并且这个判断可被证伪。** 验收标准 = 判断准不准（每个信号的取值，事后可用数据检验对错）。

职责链（总 PRD §1.2）：**数据源适配 → 指标计算 → 市场状态判定 → 信号推送**。它包含三块：

1. **信号库**：一组**可证伪的客观市场信号**（信号原子），由数据规则得出，可不断累积、可淘汰。
2. **判定与快照**：按市场驱动的节奏对每个信号求值，并把当时全部输入数据存档为**决策时点快照**。
3. **推送**：把状态切换/风险提醒发到推送通道（不含任何账户信息）。

### 0.2 三条红线（不可绕过）

1. **账户事实库零依赖**：信号层**绝不读取账户/持仓数据**——市场状态不受个人持仓影响，杜绝「重仓所以看多」的污染。（行情接口几乎全 `security=NONE`，取数本就不需要账户 key，见数据源调研。）
2. **无人工覆写入口**：信号取值**完全由数据规则得出**，不提供任何手动改写状态的入口；人能调的只有「是否追踪某信号」的开关（三态，见 §1.4），且可审计。
3. **只读、无副作用**：本层**唯一的写是决策时点快照**（存储机制借账本层容器）；除此之外零写入、零副作用，可快速迭代。

### 0.3 层间接口（契约）

| 方向 | 信号层提供 / 消费 | 说明 |
| --- | --- | --- |
| → 决策层 | **活跃信号集 + `snapshot_id`** | 决策层只消费状态信号与快照 ID，**永不直接读原始行情**（总 PRD §1.4 契约1） |
| ↔ 账本层 | 写入 / 取回**决策时点快照** | 快照**内容**由本层定义；账本层只提供容器与按 `snapshot_id` 取回（账本 PRD §0.3） |
| ← 数据源 | Binance 行情（Spot + 衍生品只读） | 详见第 3 章；ETF/美股/社交情绪为另源，Phase 1 不含 |
| ⊗ 账本账户数据 | **无此连接** | 红线：信号层不消费任何账户事实 |

> 成交记录绑定其发生时刻的 `snapshot_id`（总 PRD §1.4 契约4），但**绑定动作在账本层**；信号层只负责让该时刻有一个可被指向的快照存在。快照由市场节奏驱动产生，与用户是否交易解耦（ADR-0004 决策 5）。

### 0.4 范围（Phase 1）

**做**：
- 可证伪信号原子库 v0 + 信号注册表（唯一真相源）；
- 维度范围（第 3 章）：**P0** BTC/ETH 趋势结构、ETH/BTC 强弱（K 线）；**P1** 资金费率情绪（fundingRate）；**P2** 持仓量、多空比（影子期攒数）；
- 决策时点快照 v0（活跃信号集 + 取值 + 触发时间）；
- AI 情绪信号作为**被回测的信号源**（第 4 章，角色 A）；
- 信号推送 + 市场页/配置页/快照查看器。

**不做**（Phase 1）：
- AI 作为**元设计者**自动选信号/定阈值（ADR-0004 决策 6，角色 B，Phase 2+）；
- ETF 资金流、美股宏观、X/社交情绪等**非 Binance 数据源**（延后）；
- 微观结构信号（订单簿深度、逐笔）；
- 综合状态的复杂合成层（Phase 1 先做多维独立原子，合成留 v0.2）；
- 从页面增删改信号（信号 Phase 1 全部 hard code，配置页只读 + 开关）。

## 第 1 章 信号模型与注册表

### 1.1 心智模型

> **信号是关于市场的客观事实，不是关于「我该怎么做」的指令。信号层只生产事实；如何解读、要不要动手，是策略层的事。**

由此推出本层的形态（ADR-0004 决策 1）：

- 信号层是**一组多维独立的「信号原子」的库**，会随时间累积；不是一个被复杂规则合成出来的「单一市场状态」。
- **生产与消费分离**：不同策略的差异在于**挑选并配置同一批信号原子**（各自定阈值、各自定动作），而非每个策略要求专属信号——所以信号库不因新增策略而膨胀。
- **综合状态（若做）只是原子之上一个可选的合成层**，Phase 1 不做。

举例：`btc_trend = 下降` 且 `funding_rate = 偏高` 是两条客观事实；定投策略可能「无视、继续」，趋势策略可能「触发减仓」——信号层只陈述前者，绝不表达后者。

### 1.2 信号原子的标准结构

每个信号原子在**注册表**里按统一结构登记。这是第 1 章与第 5 章（快照）的共同地基——**每加一个信号都往这个模子里填**。

| 字段 | 含义 | 约束 |
| --- | --- | --- |
| `signal_id` | 稳定唯一标识（如 `btc_trend_structure`） | 一旦发布不可改名（快照按它引用） |
| `name` / `summary` | 人读名称与一句话简述 | — |
| `hypothesis` | **假设**：这个信号在赌市场的什么规律 | 可证伪的起点；写进信号档案 |
| `dimension` | 维度/类别（趋势 / 强弱 / 资金费率 / 持仓 / 情绪…） | 供市场页分组 |
| `value_domain` | **取值域**：枚举（如 `{上升,震荡,下降}`）或数值区间 | 必须有限可枚举或明确量纲 |
| `definition` | **可证伪判定规则 + 阈值**：什么数据条件得出什么取值 | 阈值以**常量**形式存在，卡片/页面引用它而非手抄（ADR-0004 决策 3） |
| `data_source` | 数据源接口 + period + **回填能力**（可冷启动回测 / 仅近 1 月） | 引用第 3 章 / 数据源调研 |
| `version` | 版本号；**改 definition 即产生新版本**（只追加） | 历史快照按当时版本解释 |
| `lifecycle_state` | 生命周期：`观察` / `启用` / `关闭`（见 §1.4） | 唯一运行时可变状态 |
| `backtest_spec` | **回测口径**：「准」如何定义、用什么窗口与基准衡量准确率 | 无回测口径的信号不得进入「启用」 |
| `debounce` | 防抖参数（频率限制 / 滞后 / 确认窗口） | 引用第 2 章 |
| `card_spec` | 配置页 spec 卡片所需的展示元数据 | **与判定代码同模块导出**（§1.3） |
| `depends_on` | 依赖的其它原子 / 数据（如有） | 用于一致性与失效传播 |

> `version` 与 `lifecycle_state` 的区别：前者是「定义变了」（只追加历史），后者是「现在追不追踪 / 用不用」（可变 + 可审计）。

### 1.3 信号注册表 = 唯一真相源

ADR-0004 决策 2、3 落地为本层最重要的工程约束：

- **一处定义，两处消费**：每个信号在注册表登记 §1.2 全部字段；**判定代码按注册表跑，配置页按注册表显示**——杜绝「页面写 70、代码跑 65」的漂移。这与账本层「事件流唯一真相」是同一种洁癖。
- **卡片与判定同源**：一个信号 = 一个模块，**同时导出**「判定函数」与「`card_spec`」；配置页渲染该模块导出的 spec。卡片上的**活数字**（阈值、当前取值、上次触发时间）**禁止手抄**，必须引用代码常量/运行时状态；描述性文字（假设、设计理由）可自由手写。
- **目的**：让「信号 → 快照」的完整生成逻辑摊在页面上，可对照判断代码是否合理（这是配置页存在的理由）。

> 关于「信号档案」：每个信号的一生（假设演化、版本历史、回测表现、淘汰原因、反思）记录在 `docs/signals/<signal_id>.md`（一信号一档案，只追加）。注册表是**运行时真相**，信号档案是**知识沉淀**，二者互补（ADR-0004 决策 7）。`docs/signals/` 的约定与「新增信号 checklist」在落地第一个具体信号时建立。

### 1.4 三态生命周期

信号的「追踪状态」是 Phase 1 信号层**唯一**一处运行时可变状态（ADR-0004 决策 4）：

| 状态 | 计算 | 进快照 | 推送 | 可被策略消费 | 用途 |
| --- | --- | --- | --- | --- | --- |
| **观察（影子）** | ✅ | ✅ | ❌ | ❌ | 新信号试用期：默默跑、攒回测数据，尤其供「仅近 1 月、不可回填」的情绪类信号冷启动 |
| **启用** | ✅ | ✅ | ✅ | ✅ | 正式生效 |
| **关闭 / 淘汰** | ❌ | ❌ | ❌ | ❌ | 停止计算；信号档案不删，追加淘汰原因 |

约束：

- 状态切换必须**落库 + 可审计**（谁、何时、为何切换），调性同账本层 audit。
- 进入「启用」的前置条件：①有明确 `definition` + 阈值常量；②有 `backtest_spec`；③（情绪类等不可回填者）经过足够长的观察期攒到回测数据。
- 「观察 → 启用」是默认晋升路径，不是必经——可冷启动回测的信号（K 线趋势类）可在有历史回测支撑后直接启用。

### 1.5 取值、判定与「两类触发条件」要分清

- **取值**：每个信号在每个判定时刻取 `value_domain` 内的一个值，连同输入数据一起进快照。
- **信号判定条件**（属信号定义，§1.2 `definition`）：什么数据规则把信号判成某个取值。
- **快照触发节奏**（属运行参数，第 5 章）：信号层多久跑一次判定、何时落一份快照。
- 两者**都要在配置页可见**，因为它们共同决定「信号 → 快照」的完整逻辑；但它们是不同的东西，PRD 与代码中不可混用。

### 1.6 不变式 / 约束

1. **零账户依赖**：信号求值的输入只能来自市场数据源，不得出现任何账户/持仓字段。
2. **取值可证伪**：任何信号必须有明确的 `definition` 与有限/有量纲的 `value_domain`；无法用数据条件定义的，不得作为信号。
3. **快照自洽**：快照记录「当时的活跃信号集 + 各取值 + 触发时间 + 各信号当时的 `version`」，使任意历史时点可独立还原（详见第 5 章）。
4. **定义只追加**：`definition` 变更产生新 `version`，旧版本不删；历史快照永远按其记录的 version 解释。
5. **页面不撒谎**：配置页展示的活数字必须源自注册表/运行时，禁止与代码并存第二份手抄副本。

## 第 2 章 防抖（状态切换的频率限制与滞后容忍）

### 2.0 直觉（先用大白话）

设想信号「BTC 趋势」的规则是「价格 20 万以上算上升、以下算下降」。当价格在 20 万附近来回蹭（`199,998 → 200,001 → 199,999 …`），信号就会「下降→上升→下降→上升」一分钟翻脸五次——可市场啥也没发生，只是在临界点正常波动。**这种「数据在阈值附近正常晃动、却害得信号疯狂横跳」就是抖动**；每翻一次都白白推送一条提醒、让策略白动一次手，全是噪声。

防抖 = **给信号装个「沉得住气」的过滤器，别让临界点的正常晃动骗它频繁改口。** 最常用的办法是「进和出用不同门槛」——就像**空调**设 26 度时，是「热到 27 才制冷、凉到 25 才停」，25~27 之间歇着，而不是一碰 26 就反复开关。这条缓冲带就是下文的「滞后带」。

但过滤器本身可能调得太松（真反转了半天不报）或太紧（还在抖），所以我们**把过滤前的原始值和过滤后的发布值都留档**（§2.4），好事后检查这个过滤器松紧合不合适——这正是「可证伪」信条在本章的落点。下文 §2.1–§2.5 把这件事说严谨。

### 2.1 为什么必须防抖

信号取值贴着市场数据走，原始数据在阈值附近会反复横跳，导致信号在 `上升 ↔ 震荡` 之间频繁假切换。每次切换若都推送、都被策略消费，会制造噪声与无意义的动作。总 PRD §1.2 要点3 明确要求：**状态切换需定义频率与滞后容忍，避免信号抖动**。

防抖的目标：**让「发布出去的信号」比「原始读数」更稳，但不掩盖原始读数**——证伪所需的原始值仍要进快照（§2.4）。

### 2.2 防抖手段（按需组合，参数随信号登记）

| 手段 | 含义 | 适用 |
| --- | --- | --- |
| **确认窗口（confirm）** | 新取值需**连续 N 个判定周期**保持，才正式切换 | 枚举型趋势/状态类 |
| **滞后带（hysteresis）** | 进入与退出用**两个不同阈值**（如 >70 才进「偏高」、<60 才退），中间地带维持原值 | 数值阈值型（资金费率、多空比） |
| **最小保持时间（min-dwell）** | 一个取值切入后，至少保持 T 时长才允许再切 | 抑制高频翻转 |
| **冷却期（cooldown）** | 一次切换后，下次切换前的静默期 | 控制推送频率 |

> Phase 1 默认：枚举型信号用「确认窗口」，数值阈值型信号用「滞后带」，二者均可叠加 min-dwell。具体参数值在各信号档案里定，不在本章写死。

### 2.3 防抖参数登记在注册表

每个信号的 `debounce` 字段（§1.2）登记其采用的手段与参数（如 `confirm=2 周期`、`hysteresis={enter:70, exit:60}`、`min_dwell=4h`）。防抖参数是**信号定义的一部分**，变更同样产生新 `version`（§1.6 不变式4），历史快照按当时参数解释。

### 2.4 防抖与快照：原始值与发布值都要留

快照必须**同时记录两层**，否则证伪与回测会被防抖逻辑污染：

- **原始读数 `raw_value`**：未防抖、直接由 `definition` 算出的当期取值；
- **发布值 `emitted_value`**：经防抖后对外发布、被策略消费、被推送的取值。

回测时：判断「信号准不准」用 `emitted_value`（这是实际生效的），但「防抖是否过激/过钝」要靠对比 `raw_value` 与 `emitted_value` 的切换序列来检验。两者都进快照（详见第 5 章）。

### 2.5 不变式

1. **防抖不创造取值**：`emitted_value` 只能是 `raw_value` 历史里出现过的、`value_domain` 内的值；防抖只延迟/抑制切换，不得产生新状态。
2. **防抖可证伪**：防抖参数是显式登记的规则，不得是黑箱；其松紧本身要能被回测检验。
3. **原始可还原**：任何时点的 `raw_value` 必须在快照中可取回，使「如果当时不防抖会怎样」可被复盘。

## 第 3 章 输入维度与数据源

> 本章定**做哪些维度、喂什么数据、能否冷启动回测**；每个维度下**具体信号原子的阈值与判定**留到落地该信号时在其信号档案中敲定（ADR-0004：信号定义逐个手写、可证伪、可审计）。本章不写死阈值。

### 3.1 选取原则

1. **按「回测能否冷启动」排优先级**：能用历史数据直接回测的（K 线、资金费率历史）优先；只保留近 1 个月、不可回填的（持仓量、多空比）必须靠「观察/影子期」从上线起攒数据（数据源调研 §5.2、ADR-0004 决策 4）。
2. **可证伪**：每个维度要能落成有限取值域 + 明确数据规则的信号。
3. **免费、可得、可靠**：Phase 1 只用 Binance 公开行情（`security=NONE`，无需账户 key），不引入付费/不稳定源。
4. **多源多维**：Phase 1 覆盖「Spot 价格」与「衍生品情绪」两类来源、趋势/强弱/费率/持仓/多空多个维度，作为试点既不臃肿也不单薄。

### 3.2 P0 维度（可冷启动回测 · K 线）

数据源：`GET /api/v3/klines`（Spot，weight 2，security NONE，可深度回填；数据源调研 §2.1）。

| 维度 | 候选信号原子 | 取值域形态 | 输入 | 回填 |
| --- | --- | --- | --- | --- |
| BTC 趋势结构 | `btc_trend_structure` | 枚举 `{上升, 震荡, 下降}` | BTCUSDT 日/周 K 线（均线结构、高低点序列） | ✅ 可冷启动 |
| ETH 趋势结构 | `eth_trend_structure` | 枚举 `{上升, 震荡, 下降}` | ETHUSDT K 线 | ✅ |
| ETH/BTC 强弱 | `eth_btc_strength` | 枚举 `{走强, 持平, 走弱}` | `ETHBTC` 交易对 K 线，或两条 K 线相除 | ✅ |

防抖：枚举型，默认「确认窗口」（§2.2）。生命周期入口：有历史回测支撑后可直接「启用」。

### 3.3 P1 维度（可冷启动回测 · 资金费率）

数据源：`GET /fapi/v1/fundingRate`（U 本位合约，与 `fundingInfo` 共享 500/5min 限额，历史可回填；数据源调研 §3.1）。**红线确认**：只读公开资金费率，不交易合约。

| 维度 | 候选信号原子 | 取值域形态 | 输入 | 回填 |
| --- | --- | --- | --- | --- |
| 资金费率情绪 | `btc_funding_sentiment` | 枚举 `{偏高, 中性, 偏低/负}` 或数值带 | BTCUSDT(及 ETH)永续资金费率序列 | ✅ 可冷启动 |

含义：正且偏高 = 多头拥挤付费（潜在过热）；负 = 空头付费。防抖：数值阈值型，默认「滞后带」。生命周期入口：可直接「启用」。

### 3.4 P2 维度（需影子期攒数 · 仅近 1 月）

数据源：`futures/data/*`（weight 0，限 1000/5min，**官方只保留近 1 个月**，不可历史回填；数据源调研 §3.2–3.3）。

| 维度 | 候选信号原子 | 取值域形态 | 输入 |
| --- | --- | --- | --- |
| 持仓量变化 | `btc_oi_trend` | 枚举 `{扩张, 平稳, 收缩}` | `openInterestHist`（持仓量 + 名义价值） |
| 多空比情绪 | `btc_long_short_sentiment` | 枚举 / 数值带 | `globalLongShortAccountRatio`（散户，常作反向）、`topLongShortPositionRatio`（大户持仓） |

防抖：同 P1。**生命周期入口：从上线起进「观察（影子）」态持续抓取落库**，攒够回测数据再晋升「启用」——这类信号天生无冷启动回测，影子期是其唯一的回测来源（§1.4、ADR-0004 决策 4）。

### 3.5 取数与调度约束（PRD 必须写清）

1. **地理限制硬前提**：抓数环境出口 IP 必须在 Binance 非限制区，否则全部接口返回 `Service unavailable from a restricted location`（数据源调研 §5.1）。
2. **情绪历史不可回填**：P2 信号若上线时没开影子，历史永久丢失——上线即开影子是纪律。
3. **低频轮询**：信号判定是分钟/小时级，按周期轮询 REST 即可，Phase 1 不引入 WebSocket 行情流；集中取数、避免全市场无脑拉（24hr 全市场 ticker 权重 40–80）。
4. **取数与账本解耦**：行情抓取不携带任何账户 key，独立于账本同步管道单独调度（呼应 §0.2 红线1）。
5. **实测推迟**：接口字段顺序/确切权重/保留窗口等以官方文档为准，线上实测统一推迟到非限制区环境（数据源调研 §0、§6）。

### 3.6 维度与信号原子的关系

一个维度可派生**一个或多个**信号原子（如趋势维度可同时有「日线趋势」「周线趋势」两个原子）。维度是组织/取数的单位，信号原子才是注册表与快照里的最小条目。本章只锁定 Phase 1 的维度与数据源；原子的最终清单与各自阈值随落地逐个在信号档案中确定。

## 第 4 章 AI 情绪信号

### 4.1 定位：AI 是被回测的选手，不是定规则的裁判

AI 情绪信号是「读非结构化信息（新闻 / 社交 / 公告）→ 判断市场情绪倾向」的一类信号源。本层只接受 AI 的**角色 A**——它的输出就是一个**信号原子**，登记进同一张注册表（§1.2）、遵守同一套纪律（可证伪、三态、版本化、防抖、进快照、不准则淘汰）。**不接受角色 B**：AI 不得替人决定追踪哪些信号、不得自动选阈值（ADR-0004 决策 6，Phase 2+ 才谈，且永远由人拍板）。

呼应总信条：**系统中不存在不受复盘检验的模块，AI 也不例外。** AI 信号与规则信号在系统里完全平权——唯一区别是它的「判定逻辑」是模型+提示词，而非数学规则。

### 4.2 输出必须结构化、可枚举

AI 信号的取值**不能是一段自由文本**，必须落进有限 `value_domain`：

- 取值示例：`sentiment ∈ {看多, 中性, 看空}`，可附 `confidence ∈ [0,1]`。
- 自由文本（AI 的理由陈述）只能作为**附属说明**进快照，**不能**作为被消费/被回测的信号值本身。

理由：策略层消费的是结构化取值；回测要统计准确率，也必须基于可枚举的取值。

### 4.3 来源标注与可复现（AI 特有，最关键）

AI 不确定、可能漂移，所以比规则信号**多三项强制要求**，否则不可证伪：

1. **来源标注**：AI 这次判断**读了什么**（输入的原文 / 摘要 + 来源链接 / 时间），必须随输出存进快照。没有来源 = 无法事后检验「它是不是看错了材料」。
2. **版本含模型与提示词**：`version` 字段必须包含 **model id + prompt 版本**；换模型或改提示词 = 新 `version`（§1.6 不变式4），历史快照按当时版本解释。
3. **抑制随机性**：调用尽量确定化（低 temperature / 固定参数），并在快照记录调用参数，使复盘能理解「当时 AI 为什么这么说」。

### 4.4 准确率回测口径

AI 信号同样必须有 `backtest_spec`（§1.2），且**进入「启用」前必须有回测口径**：

- 「准」如何定义：如「判看多后 N 日 BTC 上涨」的命中率，对比基准（如随机 / 始终中性）。
- 长期不准 → 走「关闭 / 淘汰」（§1.4），档案记录淘汰原因。AI 信号没有豁免权。

### 4.5 红线与零账户依赖

- AI 信号同样**只读市场/公开信息，零账户依赖**（§0.2 红线1）——不得把持仓喂给 AI「问该不该加仓」，那是策略层的事且违背证伪原则。
- **无人工覆写**：人不能手动修改 AI 的输出值；人能调的只有该信号的三态开关（可审计）。

### 4.6 Phase 1 边界与成本（开放问题）

- **架构 Phase 1 定义清楚，数据源成本待解**：优质社交情绪源（尤其 X API）成本是已知开放问题（总 PRD §5.3）。
- Phase 1 务实路径：AI 情绪信号**先以「观察（影子）」态接入**低成本 / 免费源（如公开新闻 RSS、公告），按 §1.4 攒回测数据；待证明有效且成本可接受，再考虑升级数据源与「启用」。
- 具体源选型与成本评估列入第 8 章开放问题，不在本版定死。

## 第 5 章 决策时点快照 schema

### 5.1 定位

快照是信号层**唯一的写**（§0.2 红线3），是「可复盘、可证伪」的物理载体：把每次市场状态判定时**系统看到的全部输入与得出的全部取值**原样存档，使任意历史时点可被独立还原与回测。

存储分工（账本 PRD §0.3、§1.4.9）：**账本层提供容器** `decision_snapshot = {snapshot_id, captured_at, content_ref}`；**内容 schema 由本章定义**，存为 `content_ref` 指向的存档。账本不解释内容。

### 5.2 触发节奏（解决「事件驱动 vs 周期」）

快照由**市场节奏驱动，与用户是否交易解耦**（ADR-0004 决策 5）。Phase 1 采用**周期心跳 + 事件驱动**双轨：

| 触发 | 时机 | 作用 |
| --- | --- | --- |
| **周期心跳** | 固定频率（Phase 1 默认每日，可配） | 保证时间轴连续、无洞，回测可在任意日取到一份 |
| **事件驱动** | 任一**启用**信号的 `emitted_value` 发生切换时 | 精确捕捉状态切换的那一刻 |
| 手动 | 调试 / 人工触发一次判定 | 标记 `trigger_reason=manual` |

> 成交绑定 `snapshot_id` 的动作在账本层：成交发生时指向**当时最近的一份快照**；信号层只负责让时间轴上始终有快照可指（心跳保证了这点）。

### 5.3 快照内容 schema

`content_ref` 指向的存档内容分三块：

**(a) 元信息**

| 字段 | 含义 |
| --- | --- |
| `snapshot_id` | 与账本容器一致的唯一 ID |
| `captured_at` | 判定时间 |
| `trigger_reason` | `heartbeat` / `state_change` / `manual` |
| `registry_version` | 当时信号注册表版本 |
| `schema_version` | 快照内容 schema 版本 |

**(b) 活跃信号集**（每个**观察 / 启用**态信号一条；关闭态不计算、不入快照）

| 字段 | 含义 |
| --- | --- |
| `signal_id` | 信号标识 |
| `version` | 当时该信号的定义版本（AI 信号含 model+prompt 版本） |
| `lifecycle_state` | 当时是 `观察` 还是 `启用` |
| `raw_value` | 未防抖的当期取值（§2.4） |
| `emitted_value` | 防抖后发布的取值（§2.4） |
| `confidence` | 置信度（如适用，如 AI 信号） |

**(c) 原始输入数据**（每个信号判定所**实际消费**的输入，原样存档）

| 字段 | 含义 |
| --- | --- |
| `inputs[signal_id]` | 该信号 `definition` 当时吃进的输入切片（如趋势信号的近 N 根 K 线 OHLC、资金费率序列、多空比值） |
| `ai_evidence[signal_id]` | AI 信号读的原文/摘要 + 来源链接 + 调用参数（§4.3） |
| `source_meta` | 取数时间、接口、可感知的数据延迟 |

> 「全部输入」按 `definition` **实际消费的粒度**存档（如近 200 根日线收盘价），不是存全市场全历史——既满足证伪所需的「原样还原判定」，又不让体量失控（§5.6）。

### 5.4 引用与取回

- 按 `snapshot_id` 从账本容器取回 → 解 `content_ref` 得到上述内容。
- **快照查看器**（第 7 章）据此把「当时系统看到的全部输入」摊给人看，是「可证伪」的肉眼验证入口。
- 成交行的 `snapshot_id`（账本侧绑定）可跳转到对应快照的冻结态视图。

### 5.5 体量与成本（回填账本 PRD §7.6）

按 §5.2 + §5.3 估算（替换账本 §7.6 占位）：

- **频率**：每日心跳 ≈ 365/年 + 事件切换（Phase 1 少量启用信号，估每年数百）≈ **约 1000 份/年**。
- **单份体量**：信号取值块极小（<1KB）；原始输入主要是 K 线切片（数 KB）与资金费率/多空比序列（KB 级）；**AI 证据是大头**——故 `ai_evidence` 存**摘要 + 来源链接**而非全文，单份控制在数十 KB。
- **年增量**：约 1000 × 数十 KB ≈ **数十 MB/年**，量级可忽略；与账本 §7.5「事件流+快照长期保留、不删」一致，无需分级清理。
- **控量纪律**：原始输入按 definition 消费粒度存；AI 证据存摘要+指针；不在每份快照里冗余全市场行情或全历史。

### 5.6 不变式

1. **只追加、不可变**：快照一旦写入不可改、不可删（呼应账本「事实只追加」）。
2. **自洽可独立还原**：一份快照须自带「活跃信号集 + raw/emitted 取值 + 各信号 version + 触发时间 + 实际输入」，使**脱离当前注册表也能还原当时的判定**。
3. **raw 与 emitted 都在**：防抖前后取值都留档，使「防抖松紧是否合适」可被复盘（§2.4）。
4. **时间轴无洞**：心跳保证任意日期至少有一份快照可供成交绑定与回测。
5. **零账户数据**：快照内容只含市场输入与信号取值，绝不含任何账户/持仓字段（§0.2 红线1）。

## 第 6 章 信号推送

### 6.1 定位与 Phase 1 形态

推送 = 把**状态切换 / 风险提醒**送达。**Phase 1 仅做「页面内呈现」，不接外部通道**（Telegram / 飞书等延后）。即信号动态只在市场页内可见（第 7 章「信号动态」区），不主动推到外部 IM。

### 6.2 站内呈现内容（由快照时间轴驱动）

- **状态切换记录**：哪个**启用**信号、何时、`emitted_value` 从什么变成什么，链到对应快照（事件驱动快照，§5.2）。
- **风险提醒**：达到预设条件的信号取值（如资金费率持续偏高）。
- 同步/取数异常提示（取数失败、地理限制命中等，§3.5）。

### 6.3 推送规则（红线即刻生效，为外部通道预留）

即使 Phase 1 只在页面，以下规则现在就立，避免日后开外部通道时返工：

1. **不含账户敏感信息**：推送/呈现内容只有市场信号与提醒，绝无持仓、余额、key 等任何账户数据（总 PRD §2.1、§0.2 红线1）。
2. **触发源**：仅**启用**态信号的 `emitted_value` 切换（防抖后）触发，避免抖动刷屏；观察态不触发。
3. **去重 / 冷却**：复用信号自身的防抖冷却（§2.2），不另设一套。

### 6.4 延后项

外部推送通道（Telegram / 飞书）选型、消息模板、频控与免打扰策略列入第 8 章开放问题，待 Phase 1 跑通后评估。

## 第 7 章 市场页与配置页（前端）

> 前端**直接参照** `design/数字资产投资操作系统_视觉说明.html`（token / 组件 / 系统态词表），决策依据 ADR-0002。本章只定**页面功能与模块优先级**，不另起一套视觉。

### 7.1 定位与语气

市场页对应判断层（总 PRD §2.2），**只读**：呈现「市场现在是什么状态、依据是什么、历史如何」。核心气质是**可证伪的肉眼入口**——任何判断都能点开看到支撑它的原始数据。

### 7.2 模块优先级（判断优先）

1. **当前市场状态 + 状态历史时间线**：各启用信号的当前 `emitted_value` 与切换历史；时间线每个节点链到快照。
2. **各维度数据面板**：按维度（趋势 / 强弱 / 资金费率 / 持仓 / 多空比）展示当前值与近期走势（第 3 章范围）。
3. **信号配置页**：见 §7.3。
4. **快照查看器**：见 §7.4。
5. **信号动态**：第 6 章站内呈现。

### 7.3 信号配置页（呼应 §1.3 唯一真相源）

- **一信号一张 spec 卡片**，卡片内容由该信号模块导出的 `card_spec` 渲染（与判定代码同源，§1.3）；Phase 1 不能从页面增删改信号。
- 卡片须同时展示**两类逻辑**（§1.5）：信号**判定条件**（definition + 阈值，引用代码常量，不手抄）、与**快照触发节奏**（§5.2）——使人能对照判断代码是否合理。
- 卡片含**三态开关**（观察 / 启用 / 关闭，§1.4）；切换写审计记录（谁、何时、为何）。
- 展示该信号的生命周期状态、当前 version、上次触发时间、回测口径概要。

### 7.4 快照查看器（可证伪的肉眼验证入口）

- 点击任意一次历史判定（时间线节点 / 成交的 `snapshot_id`），还原当时**全部输入与取值**：活跃信号集、`raw_value` 与 `emitted_value`、各信号 version、原始输入切片、AI 证据来源（§5.3）。
- **冻结态**：历史快照只读、按当时 version 解释，不随当前注册表变化（§5.6 不变式2）。
- 入口：状态时间线、信号动态、以及账本侧成交行的 `snapshot_id` 跳转（账本 PRD §8）。

### 7.5 视觉与交互规则

沿用视觉契约的 token / 组件 / 系统态词表；状态用契约既有的状态色与词表表达，不自造。只读页面不提供任何改写信号取值的入口（§0.2 红线2）。

### 7.6 衔接

- ← 信号注册表：配置页、数据面板的真相源。
- ← 决策时点快照：状态时间线与快照查看器的数据源。
- → 账本页：成交 `snapshot_id` 双向跳转（账本 PRD §8.6 ↔ 本章快照查看器）。
